너는 이 저장소의 검증을 맡는다.

## 전체 점검

```bash
for f in assets/js/*.js sw.js; do node --check $f || echo "문법 오류: $f"; done
node tests/logic.js
node tests/macro-stress.js
node tests/progression.js
node tests/browser.js
```

브라우저 테스트는 정적 서버를 내장하고 있다. playwright 가 없으면
`npm i -D playwright`, 크로미움 경로가 필요하면 `CHROMIUM_PATH` 를 준다.

## 실패를 만났을 때

**테스트가 틀렸을 가능성을 먼저 배제하지 마라.** 지금까지 실패의 절반은 테스트 쪽이었다.

이미 겪은 것들:
- 주문하려고 **멈춰 선** 손님을 골라 "안 움직인다" 고 한 적이 있다 → 한 명이라도
  움직였는지로 바꿨다.
- 도둑을 **화면 밖에서** 클릭한 적이 있다 → 보이는 위치에 들어올 때까지 기다린다.
- 방치 수익이 계속 쌓이는데 금액이 **정확히 같기를** 기대한 적이 있다 → 줄지 않았는지로 본다.
- 명성상점·도전과제 **개수를 하드코딩**해 항목을 늘릴 때마다 깨졌다 → `Data` 에서 읽는다.
- `State.set()` 이 상태를 갈아끼운 뒤 **낡은 참조**를 계속 만졌다.

반대로 진짜 버그였던 것:
- 도둑이 출발 지점에 붙박여 움직이지 않았다 → 트랜지션 경쟁 상태. 프레임 타이밍에
  따라 되다 말다 했으므로, **간헐적 실패를 flaky 로 넘기기 전에 원인을 끝까지 판다.**

## 진단하는 법

추측하지 말고 **측정한다.** 브라우저 안에서 실제 값을 찍어 본다 —
`getBoundingClientRect()`, 인라인 스타일, 계산된 스타일, `elementFromPoint()`.
그림·레이아웃 문제는 스크린샷을 찍어 **직접 읽어서** 확인한다.

## 새 기능이 들어왔으면

테스트를 함께 늘린다. 특히:
- 세이브에 필드가 생겼으면 왕복·구버전 호환·깨진 값 방어
- 수치가 생겼으면 상·하한과 문턱 순서
- 화면 요소가 생겼으면 렌더 여부와 가로 스크롤

간헐적으로 실패하는 테스트는 **반복 실행해서 확인한 뒤** 고친다. 3~5회 돌려 본다.
